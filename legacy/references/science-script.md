# 口播创作与检查

## 先出稿

从 content-plan.md 与原始材料直接写 voiceover-draft.md，使用 `## 口播稿` 标记正文。核心判断、依据和平台角度不重复拆成多份策划文件。已经清楚的原题和开场可以直接保留。

先读[平台表达示例](platform-writing-examples.md)；行动受阻主题可参考[已获用户反馈的修改实例](voiceover-editorial-example.md)，纯知识介绍不强制加入情绪故事。

让观众听懂一个有价值的判断。怎么开头、是否讲故事、何时给定义、要不要建议，由材料决定。不要规定冲突、反问、对话、再钩或口语词数量。短句与转折为思路服务，不为了像口播而加口癖。

通常按 45～90 秒组织；这是篇幅参考，不是每稿必须塞满的论证框架。没有真实音频只能估算，不把估算称为实测。信息讲不清时缩小范围，不强塞全部概念再不断压字。

## 一次内容检查

对照来源看原意、案例性质和结果是否保留，检查新增的解释有无依据，再通读是否自然、听者能否跟上。来源支持“某人这样说”，不等于其结论已获专业确认；疑点应补证、收窄或标为待核，不只换一种说法。

原文案例不能因未核实而自动改成假设，也不能把转述者说成当事人。新编教学示例明确为举例，不冒充原文事实。不要把内部风险标签直接塞进口播，归属和必要边界要自然且准确。

行动建议只有在本题需要时使用。呈现真正影响行动的阻力，让专业解释回应它，再给有条件的尝试；不许诺听懂即改变，也不替别人断言动机。

实质错误修正后交候选，剩余疑点附在稿后。润色建议不阻止交稿。普通出稿不启动独立 Agent 审稿，不自动无限重写；用户要求专项审阅时才针对明确疑点核对。审阅意见不能擅自增加原题没有的误区、对立或新结论。

## 确认与机器稿

先交自然口播。用户明确确认当前稿后按 video.md 转换发音、分段和停顿，保持事实与观点等价，再运行：

```bash
node <SKILL_DIR>/scripts/voiceover-qc.mjs --draft <稿件> --tts <机器稿> --confirm YES
```

确认记录自动写入已有 voiceover-report.json 并绑定当前正文。后续只调整语音标记、重跑检查可保留同正文的确认；正文变动会失效，不能自动续签。程序只检查记录和文件对应，不认证用户身份或专业语义。

不需要 script-brief.md、hook-lab.md、script-review.json 或 science-script-report.json 才能交稿、生成已确认机器稿。旧工具只供历史记录核查，不是当前验收门。视频所需的知识拍映射在收到音频后建立，不反过来强迫文案套结构。
